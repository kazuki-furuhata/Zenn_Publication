本セッションでは、Gemini Enterprise App を入口に AI を業務成果につなげていく過程で、実際に何が「壁」として現れ、どう越えたのかを、当社が支援した 2 社の事例からお話ししました。

本記事では、資料のポイントを紹介しつつ、時間の都合でスライドに載せ切れなかった判断の背景——特に「なぜその打ち手を選んだのか」——を補足します。

## なぜ「品質・コスト・浸透」という切り口にしたのか

技術は、企業が使える形で整ってきています。
回答の根拠づけと検証の仕組みがあり、従量課金で投資をコントロールでき、現場がそのまま使える形で提供される。
その代表例が Gemini Enterprise です。

しかし、プロダクトが揃っていることと、業務成果が出ることは別です。
実際の導入現場では、稟議が進まない、縦割りでデータが分断されている、従来のやり方が業務の前提になっている、といった事情があり、自社のデータ・コスト条件・業務導線に合わせる作業が必ず発生します。

セッションでは、この「合わせる作業」で現れる課題を 3 つに整理しました。

![品質・コスト・浸透の3つの壁と、それを生む土壌（縦割り・稟議・既存業務）](/images/articles/4945c084b8694f_3.png)  
*縦割り、稟議、既存業務などが壁を生む土壌になる*

| 壁 | 確認したい問い | 壁を生む土壌 |
| --- | --- | --- |
| 品質の壁 | 業務上、信頼できる結果になっているか | 縦割り |
| コストの壁 | 継続利用できる費用対効果が見込めるか | 稟議 |
| 浸透の壁 | 現場が実際の業務で使い続けられるか | 既存業務 |

重要なのは、この 3 つが技術だけから生まれるものではない、という点です。
だからこそ、技術検証と並行して確認する必要があります。

## この資料を、どう作ったか

事例に入る前に、資料の作り手として考えたことを 3 つだけ共有します。
読み進めるうえでの前提にもなるためです。

### エンジニアとアナリスト、2 つの視点で話した理由

3 つの壁は、作る側だけを見ていても、使う側だけを見ていても、全体像が掴めません。

品質とコストは基盤やパイプラインを作る側の話に見えますが、「何を正解データとするか」を決められるのは業務を理解している側です。
逆に浸透は使う側の話に見えて、応答速度やグラフの正確性という作る側の設計判断に規定されます。

今回紹介する 2 案件を実際に推進したのは、アナリストの田中です。私はその案件の担当ではなく、技術的な観点から外側で整理する立場でした。
近すぎない距離から見たことで、個別の事情に見えていたつまずきが 3 つのパターンに畳めることに気づけた——というのが、2 人で作った資料の一番の副産物でした。

### 2 つの事例を、どう並べるか

当初は「事例 A と事例 B」として横に並べる構成でした。
しかしそれだと「いろいろな会社を支援しています」という話にしかなりません。

1 社目で仮説が生まれ、2 社目でそれを検証した——という順番の物語に組み替えたことで、ようやく持ち帰れる話になったと感じています。
以降もその順番で読んでいただけると、3 つの壁がどう育っていったかが追いやすいはずです。

### つまずきを、どこまで書くか

事例紹介は成功の話に寄りがちですが、今回は「共通 ID がなかった」「ユースケースが広すぎた」といった、うまくいかなかった場面を軸に据えました。
壁の越え方を伝えるには、壁にぶつかった瞬間の解像度が必要だと考えたためです。

## 事例 1：大手エネルギー企業——コンタクトセンターの通話音声分析

1 社目は、コンタクトセンターに集まるお客様の生の声を AI で分析し、顧客対応やサービス改善につなげる取り組みです。

![音声データからGemini API、Cloud DLP、BigQuery、Looker Studioへと繋がるパイプライン構成図](/images/articles/4945c084b8694f_4.png)  
*生の声を、意思決定の根拠に*

音声データを Gemini API で発話区間ごとに文字起こし・感情分析し、続けて要件分類とインサイト抽出を実施。
Cloud DLP で個人情報を匿名化したうえで BigQuery に蓄積し、Looker Studio で応答件数や平均応答時間などの評価指標を可視化する構成としました。

この案件では、3 つの壁すべてにぶつかりました。

### 品質の壁：正解データが紐付かない

分類精度を評価しようとして、最初に詰まりました。

オペレーターが応対後に手入力した分類データは存在していたのですが、集計目的の別システムで管理されており、**AI 処理後のデータと共通する通話 ID がありませんでした**。
正解データと突き合わせられなければ、精度評価そのものができません。

![理想では共通の通話IDで突合できるが、現実には通話IDが存在しないことを示す比較図](/images/articles/4945c084b8694f_5.png)  
*共通する ID がなければ、結果の比較ができない*

打ち手として、通話 ID 以外の共通データ——オペレーター ID と応答日時——を使って間接的に結合しました。
応対直後に入力される運用だったため、時刻の近接で対応付けが成立するという読みです。

結果、AI の出力を正解データと比較できるようになり、精度改善のスタートラインに立てました。
その後のプロンプトチューニングで、分類精度は **55% から 85%** に向上し、実運用可能と判断しています。

### コストの壁：運用費が稟議を止める

「分析サービスはいろいろあるが、余計な機能があって高い。運用コストを抑えたい」というご要望をいただきました。
精度とコストはトレードオフであり、最適化が必要です。

![パイプラインのうち文字起こし工程が運用費の大半を占めることを示した図](/images/articles/4945c084b8694f_6.png)  
*運用費のほとんどを占め、かつその後のデータ精度を大きく左右する工程*

パイプライン上でコストの大半を占めていたのは文字起こしでした。
ここは同時に、後続のデータ精度を大きく左右する工程でもあります。

検討の結果、文字起こし API を差し替えました。

| | Speech-to-Text V2 | Gemini 3.1 Flash Lite |
| --- | --- | --- |
| 特性 | 音声認識に最適化 | マルチモーダル対応 |
| 単価（バッチ API） | 約 30 円 / 1 時間 | 約 16 円 / 1 時間（入力 + 出力） |

あわせて `thinking_level` を `minimal` に設定し、出力トークンを最適化しています。

差し替えにあたっては、会話内容が変化するレベルのハルシネーションが発生しないかを検証しました。
結果として、その後のデータ処理に影響があるほどのハルシネーションは確認されず、**文字起こしコストを約 50% 削減**できました。

:::message
記載の単価は検証時点のものです。最新の価格は公式のリファレンスをご確認ください。
:::

### 浸透の壁：会議でそのまま使えるのか

「会議中に出た質問に、根拠付きで回答したい」というご要望に対して、確認すべき点は 3 つありました。
応答速度はどのくらいか、グラフは描画できるか、描画されたグラフは正しいか。

10 を超えるシナリオで検証し、高々 2 分程度で回答できること、9 タイプの基本的なグラフを数値も正確に描画できることを確認しました。

![質問に対して根拠付きの回答とグラフが返る実出力の画面](/images/articles/4945c084b8694f_7.png)  
*画像はランダムな値で作成したものです*

ここで効いたのは、資料で説明するのではなく**実出力でご覧いただいた**ことです。
会議中に出た質問に、その会議のうちに根拠も揃えて回答できる。
この価値をご納得いただき、社内報告用の動画もあわせて提供しました。

### 1 社目から生まれた仮説

3 つの壁への打ち手と結果を整理すると、次のようになります。

![3つの壁それぞれに対する打ち手と結果をまとめた一覧](/images/articles/4945c084b8694f_8.png)  
*3 つの壁に対する打ち手と結果*

| 壁 | 打ち手 | 結果 |
| --- | --- | --- |
| 品質 | 共通する他のデータで間接的に紐付けた | 精度評価が可能に。その後の改善で 55% → 85% |
| コスト | API の差し替えと推論量の調整 | 稟議が通り、予算確保 |
| 浸透 | 想定シナリオで検証し、実出力で見せた | 会議中の有用性にご納得いただけた |

ここから、ひとつの仮説が生まれました。
**壁が現れてから対処するのではなく、実データと実出力で、この 3 つを導入初期から検証すべきではないか。**

## 事例 2：大手大学法人——散在データの統合とエンロールメントマネジメント

2 社目は、入学前・在学中・卒業後まで一貫した学生サポート（エンロールメントマネジメント）を実現するため、学内に散在するデータを統合する取り組みです。

![複数のデータソースをBigQueryに集約し、Dataformで加工してLooker Studioで可視化する構成図](/images/articles/4945c084b8694f_9.png)  
*散らばっていたデータを、一つに*

高校訪問実績、HP アクセス、学内アンケート結果、出願データ、進学実績、広告データ、デジタル媒体ログなどを BigQuery に集約し、Dataform で前処理・中間集計を行い、Looker Studio で入学前ファネルや在学生評価の KGI・KPI を可視化しました。

この案件では、1 社目で見えた 3 つの観点を、**着手前に確認**しました。
データ接続に必要な key が揃っているかを早期に確認し、小規模 PoC で本番化の条件を見通す。先回りしたつもりでした。

### 想定外の浸透の壁

それでも、想定していなかった形で浸透の壁が現れます。

> AI を使いたいけど、何を聞けばいいのか分からない

データもユースケースも多岐にわたる基盤を用意したことが、逆に現場を止めていました。
**想定ユースケースが広範すぎた**のです。

打ち手として、まずは業務内容と判断対象が明確なユースケースに絞りました。
具体的には、年間 1,000 件を超えるイベント参加 / 訪問オファーの選定に限定しています。

これがファーストステップになり、その後は他業務への追加要望もいただけるようになりました。

### 先回りしていたから、想定外にも対処できた

この案件で学んだのは、先回りしても想定外の壁は現れる、ということです。
ただし、**先回りしていたからこそ、想定外の壁が現れても対処する時間が残っていました**。

先回りの価値は、壁をゼロにすることではなく、時間の余裕を作ることにあります。
逆に言えば、先回りしていなければ、2 社目でも 1 社目と同じ順番でつまずいていたはずです。

データを繋いでから正解データがないと気づき、本番構築の見積もりを出してから稟議で止まり、納品してから使われないと分かる。
壁は「後で気づく」ほど手戻りが大きくなり、しかも気づくのは常に一番手戻りの大きいタイミングです。

3 つの壁は、業種が変わっても、ユースケースが変わっても、同じ場所に現れます。
事前に知っていれば確認作業で済むものが、知らなければ毎回プロジェクトの危機として現れる。
それが、2 社目で得た一番の実感でした。

## 突破の定跡——次に進むための 3 つの問い

業種もユースケースも違う 2 社ですが、共通していたのは、成果につなげる際に品質・コスト・浸透の 3 観点を確認する必要があった、という点です。

実装の定跡とは、**この 3 つが課題になりうる前提で早い段階に検証し、次へ進む条件を整えること**だと考えています。

最初から全部を決める必要はありません。PoC で壁を先に洗い出し、協議しながら本番導入する。判断の目安は次の 3 問です。

- **品質**：評価に必要なデータはつながっているか
- **コスト**：小さく試して、本番時の費用を見通せるか
- **浸透**：最初に使う業務・ユースケースを絞れているか

1 つでも No なら、そこから条件を整えていきます。

![品質・コスト・浸透それぞれの先回りの手札をまとめたスライド](/images/articles/4945c084b8694f_10.png)  
*2 つの先行事例から得た、AI を業務成果につなげるための先回りの手札*

そして、2 つの先行事例から得た「先回りの手札」は次のとおりです。

- **品質**：データをつなぎ、実出力で評価する
- **コスト**：小さく試し、本番コストを実測する
- **浸透**：最初のユースケースを絞り、業務の中で体験してもらう

## おわりに

AI を業務成果につなげる過程では、必ず自社固有の条件と向き合うことになります。
そこで現れる課題は、品質・コスト・浸透の 3 つに整理できる、というのが 2 社の支援から得た実感です。

3 つの壁には越え方があります。
この記事が、これから Gemini Enterprise App の導入を検討される方の出発点になれば幸いです。
